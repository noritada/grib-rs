# Unrecognized GRIB template numbers can cause panics during parameter access or decoder construction

## Summary

Applications that process untrusted GRIB2 data with `grib` may panic when reading parameters for grid definition, product definition, or data representation templates that the corresponding template deserializer does not recognize. The issue also affects data representation decoder construction. Decoding grid point values is not required.

## Affected usage and impact

A message can pass initial file parsing and then trigger a panic through any of these operations:

- `SubMessage::section3()`, when reading parameters for an unrecognized grid definition template.
- `SubMessage::section4()`, when reading parameters for an unrecognized product definition template.
- `SubMessage::section5()`, when reading parameters for an unrecognized data representation template.
- `Grib2SubmessageDecoder::new()` or `Grib2SubmessageDecoder::from()`, when constructing a decoder for an unrecognized data representation template, before `dispatch()` is called.

Direct use of the corresponding generated template deserializers is also affected. These interfaces return `Result`, but the unrecognized-template path panics instead of returning an error.

Applications that inspect or display section parameters can therefore be affected even if they never construct a value decoder. Initial message parsing alone does not trigger these paths. The trigger is a number absent from the corresponding template enum, which may be a valid GRIB template not yet implemented by the library; the input need not be malformed. Other accessors and operations that already reject unsupported templates are not necessarily affected.

A panic does not necessarily cause denial of service. Depending on the application's panic handling and build settings, it may interrupt a processing thread or terminate the process. This can become a denial-of-service vulnerability when an attacker can supply input to the affected operation and the resulting failure disrupts service for legitimate users. A failure confined to the attacker's request does not by itself establish service-wide denial of service; the impact depends on how the application isolates failures and maintains processing capacity.

No confidentiality or integrity impact has been established.

## Cause

The generated deserializers for `GridDefinitionTemplate`, `ProductDefinitionTemplate`, and `DataRepresentationTemplate` share a fallback branch that panics for an unrecognized discriminator. The section-parameter accessors and decoder constructor invoke these deserializers, so their usual error propagation does not handle this case.

## Mitigation and remediation

Upgrade the `grib` crate to version **0.18.6**, which fixes this issue.

## Version and publication status

The final version of [GHSA-6j96-629m-89w4](https://github.com/noritada/grib-rs/security/advisories/GHSA-6j96-629m-89w4). The fix is confirmed in `grib` version **0.18.6**. Affected versions of `grib`: `>= 0.13.1, < 0.18.6`.
